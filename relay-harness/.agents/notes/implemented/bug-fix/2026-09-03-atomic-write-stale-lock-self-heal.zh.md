# Agent Note: 陈旧写入锁在同主机且所有者可证死亡时自愈

Status: implemented

[English](2026-09-03-atomic-write-stale-lock-self-heal.md) | 中文

## 问题

`withFileLock` 的 `<file>.lock` 兄弟文件创建于 `writeFile` 与 `finally` 移除之间，因此写入方被 `kill -9`、崩溃或断电杀掉后会把锁永久留在磁盘上。此后该文件的每一个写入方——每一次凭据设置/清除（`rlh-credentials-local`）、每一次设置修改（`rlh-settings-file`），以及预设、skill 清单、MCP server 文件和 `fs-local`——都要撑满 2 秒退避期限然后失败。恢复是操作者动作，而仓库内没有任何代码清扫陈旧锁，于是一个遗留锁就能让这些写入瘫痪，直到人工删除。

## 决策

锁内容现在在所有者 pid 之外同时记录所有者主机（`pid\nhost\n`；全仓库核查确认没有其他读取方解析该内容，格式变更安全）。竞争时，退避之前，竞争者读取锁文件，且仅在两个条件同时成立时移除它：记录的主机等于 `os.hostname()`，并且 `process.kill(pid, 0)` 抛出 `ESRCH`——唯一能证明所有者进程已不存在的信号。完成自愈的竞争者立即重试获取。

其余一切歧义结果都留在既有的退避加超时路径上响亮失败：不可读或畸形的锁内容、外来主机的锁（共享文件系统部署的锁绝不能被另一台机器删除）、存活的所有者——信号探测返回 `EPERM` 表示该 pid 在另一用户下存在，按存活处理而不自愈——以及移除后窗口内被其他竞争者重建的锁。主机重启后 pid 被复用的情况按存活处理，仍是操作者动作；没有零依赖的可移植启动标识可以关闭该窗口，因此选择文档化而非绕行。

协议常量保持固定：`LOCK_TIMEOUT_MS` 与重试曲线不变，自愈不设 Config 字段——它是锁协议的正确性属性，不是随部署变化的选择。

## 已考虑的替代方案

**按文件锁龄自愈。** 拒绝：此前立场的核心理由依然成立——锁龄无法区分已崩溃的所有者与被暂停但仍存活的写入方。主机加存活证明用证据取代了猜测。

**把 `process.kill(pid, 0)` 返回的 `EPERM` 视为已死。** 拒绝：`EPERM` 证明进程在另一用户下存在。删除其锁会破坏存活的跨用户写入方；按存活处理并响亮失败才是正确方向。

**同主机清扫时移除锁而不做存活检查。** 与锁龄方案同理被拒：没有 `ESRCH` 证据，清扫会删除存活的锁。

## 后果

锁创建与释放之间的崩溃或 `kill -9` 不再永久瘫痪该机器上的凭据、设置与预设写入：下一个竞争者移除可证死亡的锁并继续。安全方向是单调的——只要存在任何歧义，今天的结果（超时）就是最终结果，且存活所有者的锁绝不会被删除，因为存活 pid 对信号探测返回成功或 `EPERM`。消费方无需改动；它们只会看到更少的锁超时。旧版本写入的单行 pid 锁内容无法通过主机匹配，会回退到操作者移除路径，直到操作者一次性清理。
