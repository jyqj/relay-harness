# Agent Note: 本地任务注册表的终止记录保留策略

Status: implemented

[English](2026-09-03-jobs-terminal-record-retention.md) | 中文

## 问题

`LocalJobRegistry` 从不删除终止记录。只有 owner scope 销毁和服务停机会移除行，因此无 owner 的任务完全没有删除路径：每次结算都会让记录存活整个进程生命周期，模型可见的 `list()`——以及每个 `onJobsChanged` 消费者重读的可见集——会在长驻 agent 上无界增长。

## 决策

注册表现在用两个经校验的 `Config` 字段约束终止记录保留：`terminalRetentionMs`（正的安全整数，默认 `60000`）与 `maxTerminalRecords`（正的安全整数，默认 `100`）。终止记录只有在已报告（完成通知可送达）且宽限期结束后才可回收；超过每桶上限时，丢弃最早结算的已报告记录。扫描只在 `start()` 与 `list()` 时运行，从不依赖定时器，且每个受影响 owner 的可见集变更会像 owner 销毁移除一样被公告。

保留策略永不丢弃未报告的终止记录，因此完成通知保持至少一次送达。已回收的 id 在所有访问路径中读作 `unknown job <id>`——沿用既有的响亮失败行为，无需新增代码。

## 已考虑的替代方案

**仅按记录数量设上限。** 已否决：过低的 cap 可能在任何报告方送达通知之前就回收已结算任务；保护送达的是 reported 门，而不是 cap。

**结算时立即回收。** 已否决：通知报告方在结算后合法地立即重读记录；只在入口点（`start()`、`list()`）扫描可以保持结算读取路径不受影响。

**后台扫描定时器。** 已否决：两个入口点本就要遍历 store，空闲注册表的定时器只增加生命周期面，却不缩短任何有意义的保留延迟。

## 后果

在 terminal + reported + 宽限之后——或超出所在桶 cap——读取任务会得到 `unknown job <id>` 而非过期快照，job 列表随记录过期而缩短。已剪 id 的 `job_output` 以其从未存在过的 id 相同的消息响亮失败。在默认 60 秒窗口内读取任务、或通过 `read`/`wait`/`kill` 保持任务已报告的合法工作流不受影响。无界增长现在要求记录永远不变为已报告，而等待方路径已经约束了这一面。
