# Agent Note：限制 Agent inbox 保留量

状态：已实现

[English](2026-08-31-bounded-agent-inbox.md) | 中文

## 问题

Agent 拥有持久化的 `next-turn` 与 `next-step` 队列，但两者合计的实时保留量没有部署上限。停滞的 Agent，或生产速度高于模型循环的生产方，因此可以保留任意数量的完整 `UserMessage` 值与持久 splice 事件。

## 决策

`AgentLoop` 拥有仅由部署方配置的两项上限：两份待处理列表合计 4096 条消息，以及 64 MiB 的无损 JSON 消息数据。`Inbox` 会在追加实时 `agent/inbox/spliced` 事件之前校验两项投影合计，因此超限插入既不会发布持久状态，也不会发布实时通知。它会在回放和变更每份列表时增量维护字节账本；达到上限时仍可执行替换和删除。

回放持久 inbox 状态时不强制后来下调的上限。这样有意保留既有状态，使部署仍能恢复并排空它；只有后续实时变更仍会使队列高于上限时才拒绝。构造器仍拒绝非法容量，插件 schema 与直接构造校验都要求正的安全整数。

## 已考虑的替代方案

**丢弃最旧的待处理提示词。** 拒绝，因为这会静默丢失已接受的用户工作，并创造调用方无法可靠观测的队列语义。

**在回放持久事件时应用上限。** 拒绝，因为下调配置会让原本有效的 Session 永久无法加载，连取消或排空都无法进行。

**把上限暴露为实时 Settings。** 拒绝，因为它是部署资源策略，而不是用户拥有的模型行为。重启可明确启用新的准入策略，同时保留已持久化工作。

## 后果

每个具体 `ReactLoopAgent` 现在默认都有有限的待处理消息准入。生产方会在提交前收到类型化 `InboxCapacityError` 或 `InboxByteCapacityError`，并可在工作排空后重试。字节上限计量完整的无损 JSON `UserMessage`，包括内联附件元数据与内容；外部引用的 blob 存储仍由附件／存储 seam 拥有。
